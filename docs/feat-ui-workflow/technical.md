Относится к [spec.md](spec.md), ревизия 3; исходный [intent.md](intent.md), принятая ревизия 9. Принято вместе со спецификацией при переходе пользователя к реализации (2026-09-18).

Снимок исследования: `49747eb` (intent поверх `2234f98`).

- [Общий SDLC-контракт](../../skills/sdlc-setup/references/workflow.md) v2 содержит обязательный setup и требования к принятым intent/spec/plan. Применение его целиком к UI-тройке нарушит согласованное самостоятельное использование.

- Отдельного docs/sdlc/project.md в этом репозитории нет. Продуктовая спецификация не устанавливает новые правила качества для всего репозитория.
- Изменения README в PR #2 находятся в другой ветке. При будущей интеграции сохранить согласованную структуру README с SDLC на первом месте; не восстанавливать старый текст из базы этой ветки.

## Границы ответственности

| Часть | Ответственность |
| --- | --- |
| sdlc-ui-kit | Исследование, интервью, согласование набора, создание/обновление компонентов, документации и витрины |
| sdlc-ui-implement | Интервью по экрану, композиция и интеграция в приложение, проверка результата, возврат после согласованного дополнения набора |
| sdlc-ui-review | Фиксация проверяемого состояния, анализ исходников и отображения, отчёт без исправлений |
| Общий UI-контракт | Обнаружение UI Kit, источники правил, границы самостоятельного использования, принятие изменений и понятие полноты проверки |
| Установщики | Доставка согласованных комплектов инструкций и всех их ресурсов |

Общий UI-контракт предлагается хранить в references скилла sdlc-ui-kit, рядом с компактными шаблонами каталога и отчёта. Два других скилла ссылаются на него относительно своей папки. В UI-контракт не копируются обязательное SDLC-onboarding и стадийные разрешения на реализацию.

Общий SDLC-контракт должен явно ограничить обязательный setup основными семью стадиями и указать самостоятельные UI-точки входа. Это уточнение области применения, а не изменение порядка основной SDLC-цепочки. UI-скиллы читают существующие проектные политики; отсутствие SDLC-профиля само по себе не вызывает setup, настройку CRAP или mutation tooling.

Первая версия — инструкции, небольшие шаблоны и поддерживающие документы. Отдельный генератор приложений, адаптер на каждый framework и универсальный движок сравнения скриншотов не требуются. Агент работает со стеком и доступными инструментами целевого проекта. При отсутствии нужной возможности сообщает конкретную непроверенную часть.

## Артефакты целевого продукта

Сначала искать существующую библиотеку компонентов, каталог и принятые правила. Не переносить исходники и документы только ради структуры ниже. Предлагаемое расположение при отсутствии соглашений:

| Артефакт | Минимальное содержимое |
| --- | --- |
| docs/ui-kit/index.md | Принятый объём, состояние набора, ревизия и запись о согласовании; стек; пути к общим исходникам; команда и адрес витрины; ссылки на правила и каталог |
| docs/ui-kit/rules.md | Стабильные идентификаторы принятых визуальных правил, ссылки на реальные источники токенов, правила сочетания компонентов, согласованные responsive-сценарии и интерактивные требования |
| docs/ui-kit/components.md | Идентификатор и назначение компонента; путь и способ использования общей реализации; поддерживаемые варианты/состояния; ссылка на пример в витрине; границы применения |
| Общие исходники в принятой структуре проекта | Реальные токены, базовые и составные компоненты, используемые продуктом и витриной |
| Витрина | Страница проекта или существующая витрина компонентов; команда запуска и адрес для просмотра визуальных примеров тех же компонентов |

Документация — указатель на действующие исходники и принятые решения. Значения токенов и определения компонентов не дублируются в отдельной якобы канонической HTML/CSS-копии. Существующая сторонняя библиотека может быть основой UI Kit; каталог фиксирует принятую конфигурацию, допустимые варианты и способ использования.

Новый составной компонент нужен, когда появляется самостоятельный переиспользуемый интерфейс, вариант или правило. Обычная разметка экрана из существующих элементов не регистрируется как новый компонент автоматически. Новые визуальные решения и произвольные токены требуют обсуждения.

Для незнакомого проекта с несколькими витринами или UI Kit агент спрашивает, какой набор относится к задаче. Не выбирает произвольно и не унифицирует весь monorepo.

## Жизненный цикл UI Kit

- `draft`: исходное исследование или предложения с непринятыми решениями. Наблюдаемые в продукте варианты ещё не являются новым стандартом.
- `incomplete`: выбранное решение согласовано, но отсутствует часть реализации, витрины или необходимой проверки. Документ содержит конкретный пробел и следующий шаг.
- `ready`: согласованный объём реализован в общих исходниках, отражён в документах и витрине и проверен в доступных согласованных сценариях.

Материальное изменение правил или публичных возможностей компонента увеличивает ревизию. Запись согласования относится к конкретному набору изменений. Ранее согласованный объём не требует повторного подтверждения в той же сессии. Изменённый исходный код не считается проверенным только потому, что в index.md сохранился старый статус ready.

При дополнении агент показывает потребность, предложенный вариант и известные затронутые потребители. После разрешения обновляет общую реализацию, примеры, каталог и релевантную проверку. При сбое оставляет явный неполный результат, а не подтверждает соответствие. Проверки привязываются к ревизии набора и фактическому состоянию исходников.

Если при brownfield-извлечении нельзя создать общую реализацию без изменения старых экранов, согласовать узкий необходимый объём либо оставить выбранное направление предложением. Обязательство не мигрировать весь продукт не запрещает явно согласованные изменения, необходимые для текущего компонента.

## Интервью и интеграция с задачей

UI Kit: после анализа уточнить назначение продукта и первые сценарии; визуальные предпочтения и референсы; необходимые компоненты, состояния и размеры экранов; доступность и взаимодействия. Предлагать обоснованный вариант и спрашивать по одному существенному решению. Не заставлять заполнять все темы, если ответы уже есть в проекте.

Экран: цель и пользователи; действия, данные и переходы; состояния загрузки, пустоты и ошибок там, где они нужны; целевые размеры и существующие ограничения. Подтвердить конкретный объём, если ранее он ещё не согласован. Не выдумывать бэкенд-контракт: при отсутствии необходимого API показать зависимость и согласовать объём интеграции; тестовые данные не выдаются за готовую бизнес-функцию.

При наличии feature-документов использовать их пути и требования; при самостоятельном вызове записать краткие решения и результаты в выбранном каталоге работы. Не генерировать фиктивные intent/spec/plan только ради формального соответствия SDLC.

## UI review и доказательства

Вход: принятый UI Kit и конкретный scope — маршрут, экран, компоненты или diff. Для изменения фиксируется база; для всех режимов фиксируется проверяемое состояние исходников, включая незакоммиченные изменения, если они есть. Предсуществующие расхождения вне scope не превращаются в требование переписать продукт.

Проверка кода и рендера дополняют друг друга: импорт общего компонента не гарантирует правильного вида, а визуальное совпадение не доказывает правильного повторного использования. Проверять доступные релевантные состояния и согласованные размеры, не ограничиваться случайным desktop-скриншотом.

Предлагаемый отчёт — ui-review.md в каталоге задачи, с отдельной папкой визуальных свидетельств при необходимости. При отсутствии каталога предложить docs/ui-reviews/<scope>/; повторный запуск обновляет тот же scope, сохраняя различимость проверенных снимков. В отчёте:

- Ревизия UI Kit, снимок кода, маршрут/компоненты, состояния и размеры, способ запуска.
- Вердикт: соответствует в проверенном объёме; есть расхождения; проверка неполна. Список доступных проверок обязателен для толкования вердикта.
- Для замечания: место, правило/компонент, ожидаемое и наблюдаемое поведение, последствие, доказательство и предлагаемое решение.
- Отдельно: пробелы в UI Kit и недоступные проверки. Они не являются придуманными нарушениями, но могут мешать полному выводу.

Скилл не меняет приложение, набор, зависимости, CI, эталонные изображения и статус принятых правил. Допустимы сам отчёт и его визуальные материалы. Использует существующую возможность запуска/просмотра в разрешённой среде; если для неё нужны изменения проекта, сообщает препятствие. Отсутствие браузера, исходников или принятого набора не подменяется полным положительным verdict.

## Установка и совместимость

Полный комплект sdlc содержит основные семь скиллов и три UI-скилла. Дополнительный комплект sdlc-ui содержит только UI-тройку и все её общие ресурсы. Основной entrypoint полного комплекта остаётся sdlc-setup, UI-комплекта — sdlc-ui-kit. Каждый UI-скилл можно вызывать отдельно после установки комплекта.

Оба установщика разрешают комплект по явному списку и одинаково обрабатывают имена; shell не должен принять sdlc-ui за запрещённый одиночный sdlc-* до разрешения комплектов. Существующие --target, --global, --lang, --force, проверка конфликтов до записи и замена устаревших файлов сохраняются. Обновление существующей установки использует существующее правило --force; автоудаления или миграции личных файлов нет.

UI-тройка не имеет обязательных ссылок на отсутствующие в sdlc-ui основные семь скиллов. Для агента без механизма вызова скилла разрешено прочитать соответствующий установленный SKILL.md и следовать ему. Изменения пользовательского UI Kit не перезаписываются установкой пакета инструкций.

Рассмотренная альтернатива: поставлять UI только отдельным комплектом, оставив sdlc из семи. Это сохраняет прежний размер установки, но требует второй команды для полного семейства. Пользователь выбрал полный sdlc из 10 плюс отдельный sdlc-ui из трёх, чтобы всё семейство устанавливалось одной командой и сохранялась возможность установить только UI-часть.

## Стратегия проверки реализации

Проверки артефактов: валидные metadata/frontmatter, разрешимые относительные ссылки и комплектность публикации. Расширить существующие проверки установщиков для согласованных комплектов, обоих scope и всех четырёх агентов; сохранить проверки конфликтов, --force, архива npm и shell без терминала. Не заменять ожидаемый состав комплекта чтением того же манифеста так, чтобы тест не мог обнаружить пропуск нового скилла.

Поведенческие прогоны в изолированных проектах проверяют результаты, а не наличие фраз в SKILL.md:

| Сценарий | Что доказывает |
| --- | --- |
| Greenfield, простой web-стек | Интервью задаёт ограниченный состав; витрина и экран используют общие источники — R1, R2 |
| Существующий React-проект с несколькими кнопками | Исследование и выбор канонического варианта предшествуют изменениям; массовой миграции нет — R2, R3 |
| Экран с недостающим компонентом | Самовольный вариант не добавлен; после согласования набор обновлён, исходная задача продолжена — R4, R5, R10 |
| Копия компонента, локальное переопределение и несогласованный вариант | Review находит расхождения и указывает доказательства из кода и рендера — R6 |
| Корректная композиция разрешённых компонентов | Review не требует регистрировать каждую разметку как новый компонент — R6, R7 |
| Правила неполны или браузер недоступен | Чёткий частичный отчёт без выдуманных норм и полного pass — R7 |
| Review завершён | Сравнение дерева до/после подтверждает, что изменились только отчёт и его материалы — R7 |
| Есть SDLC-профиль / профиля нет | Существующие решения сохраняются; отсутствие профиля не запускает обязательный полный setup — R8 |

Для реалистичной проверки скиллов использовать отдельные оценочные сессии или независимых агентов, если это доступно и разрешено. Входом служат задача и исходные артефакты, а не заранее подсказанный ответ. Не заявлять поддержку всех web-фреймворков по одному прогону: общий контракт адаптируется к стеку, конкретные проверенные сценарии перечисляются в результатах.
