# Три скилла SDLC для разработки web UI

## Проблема и пользователи

При разработке продукта с AI-агентом модель может заново придумывать стили и компоненты для каждого экрана. Нужен общий UI Kit, понятный пользователю и агенту, процесс создания экранов на его основе и проверка соответствия.

Для людей, разрабатывающих web-продукты с AI-агентами. Три скилла входят в семейство SDLC и могут использоваться самостоятельно. При наличии проектных SDLC-настроек и согласованных документов они учитывают их и переиспользуют принятые решения; обязательный проход intent → spec → tickets для отдельного вызова не требуется.

## Желаемый процесс

1. **Создать UI Kit через интервью.** Для нового продукта начать с интервью. Для существующего сначала исследовать продукт, показать найденные варианты и выбрать с пользователем канонические компоненты. Начальный объём — визуальные основы и компоненты для выбранных пользовательских сценариев.
2. **Создать рабочие экраны.** Уточнить задачу через интервью и реализовать UI в стеке проекта из общих компонентов. Если компонента не хватает, обсудить использование имеющихся элементов либо расширение UI Kit.
3. **Провести UI review.** Проверить код и отрисованный интерфейс по UI Kit, показать отчёт и предложить решения. Review самостоятельно ничего не исправляет.

## Результаты и наблюдаемый успех

- **O1 — Согласованный UI Kit.** Есть цвета, типографика, размеры, отступы, сетка, необходимые базовые элементы и составные компоненты. Состав определяется первыми выбранными сценариями; набор расширяется при появлении новых задач.
- **O2 — Общая реализация и визуальная витрина.** Пользователь получает HTML-витрину UI Kit, агент — удобные для чтения и использования исходники в стеке проекта. Витрина и рабочие экраны используют одни компоненты и стили: изменение общего компонента отражается в обоих местах. HTML/CSS/JS — возможный формат, а не ограничение исходников для всех стеков.
- **O3 — Осмысленный старт в существующем продукте.** Анализ реального UI предшествует интервью. Существующие варианты показываются пользователю; стандартом становится согласованный набор. Миграция старых экранов на него — отдельная задача с согласованным объёмом.
- **O4 — Рабочие экраны в стеке проекта.** Второй скилл меняет исходники продукта: например, создаёт React-экран в React-проекте. Использует UI Kit; недостающие компоненты обсуждает с пользователем до их добавления. Отдельный демонстрационный макет не заменяет рабочую реализацию.
- **O5 — Конкретный отчёт о соответствии.** Review проверяет использование общих компонентов, стили, правила компоновки, предусмотренные UI Kit состояния и адаптивность. Для расхождения указывает место, нарушенное правило, предлагаемое решение и визуальное подтверждение там, где оно полезно. Самостоятельно не меняет код, UI Kit или рабочий интерфейс.
- **O6 — Согласованное развитие набора.** Новый экран или review могут выявить потребность в дополнении UI Kit. Пользователь выбирает, исправить интерфейс по существующим правилам или расширить набор. Применение изменений по результатам review требует отдельного запроса пользователя.

## Ограничения и вне объёма

- Первая версия — только web; нативные мобильные и desktop-интерфейсы вне объёма.
- Конкретный стек берётся из проекта. Способ согласования стека для нового проекта предстоит описать в спецификации.
- UI Kit и создание экранов включают интервью. Существующие согласованные решения используются повторно.
- Визуальная витрина показывает реальные общие компоненты продукта, а не отдельные имитации для демонстрации.
- Создание UI Kit не включает массовую миграцию существующих экранов.
- UI review — проверка по согласованному UI Kit. Общий UX-аудит и субъективные эстетические предпочтения вне объёма.
- Текущая задача ограничена подготовкой и коммитом принятого intent; реализация скиллов и публикация не запрошены.

## Решения для следующей стадии

На стадии спецификации определить имена скиллов, контракт файлов и витрины, способ установки и подключения к семейству SDLC, инструменты визуальной проверки и порядок обновления связанных материалов.

В сценариях интервью описать, как согласуются отсутствующий стек, необходимые состояния компонентов, размеры экранов и требования доступности. Их конкретные значения зависят от целевого проекта; универсальные значения этим intent не устанавливаются.

## Статус согласования

Источник требований — запрос пользователя и последующее интервью. Пользователь согласовал рабочие экраны в стеке проекта, общие компоненты витрины и продукта, отдельную brownfield-миграцию, review только с отчётом, проверку кода и отрисованного UI, web-only объём, принадлежность семейству SDLC при самостоятельном использовании и начальный UI Kit под выбранные сценарии.
