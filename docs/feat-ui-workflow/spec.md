# UI-скиллы семейства SDLC

## Предлагаемое решение

Три скилла ведут работу от согласованного UI Kit до рабочего web-экрана и отчёта о соответствии. Они используют исходники и инструменты целевого проекта. Визуальные правила, каталог компонентов и решения сохраняются рядом с кодом, чтобы следующая сессия или другой агент продолжили тот же процесс.

| Скилл — предлагаемые имена | Назначение | Результат |
| --- | --- | --- |
| `sdlc-ui-kit` | Создать или расширить UI Kit через интервью | Общие компоненты и стили, визуальная витрина, документы для агента |
| `sdlc-ui-implement` | Создать рабочий экран из UI Kit | Изменения в приложении, проверенные состояния и краткий отчёт о выполнении |
| `sdlc-ui-review` | Проверить соответствие UI Kit | Отчёт с конкретными расхождениями и предложениями; без исправлений |

Это часть семейства SDLC с самостоятельными точками входа. Наличие intent/spec/tickets и полный `sdlc-setup` не требуются для отдельного UI-запроса. Если такие документы уже есть, они определяют согласованный объём и правила проекта.

Полный комплект `sdlc` устанавливает все 10 скиллов: семь основных и три UI-скилла. Отдельный `sdlc-ui` устанавливает только UI-тройку со всеми необходимыми общими ресурсами. Оба способа поддерживаются Node- и shell-установщиками; сохраняется ручная установка для поддерживаемых агентов.

## Как это выглядит для пользователя

### Создание или расширение UI Kit

Скилл изучает проект: стек, стили, библиотеку компонентов, существующую витрину и правила разработки. В новом проекте без выбранного стека сначала предлагает подходящий вариант и согласует его. Стек существующего проекта сохраняется.

В brownfield скилл показывает найденные варианты компонентов и различия между ними. Пользователь выбирает канонические варианты. Затем интервью уточняет первые пользовательские сценарии, визуальное направление, нужные компоненты, состояния и размеры экранов. Вопросы задаются по одному; факты из проекта агент выясняет сам.

После согласования скилл создаёт или оформляет общий набор и показывает его в витрине. В проекте переиспользуются подходящие существующие компоненты и токены. Если нужен новый общий компонент, его витрина и будущие экраны используют одну реализацию. Для уже существующих экранов отдельно фиксируется будущая миграция; массовая переделка не входит в этот вызов.

Витрина — браузерная страница, запускаемая средствами проекта, либо уже существующая витрина компонентов. Пользователь получает ссылку и команду запуска. Витрина показывает реальные компоненты, варианты, состояния и примеры составных элементов. Этот способ доставки согласован с пользователем; самостоятельный HTML-файл не требуется.

### Создание экрана

Скилл читает принятый UI Kit и уточняет задачу: назначение экрана, действия пользователя, доступные данные, нужные состояния и адаптивность. Существующая спецификация заменяет уже отвеченные вопросы.

Экран создаётся непосредственно в приложении. Агент использует компоненты, токены и правила компоновки UI Kit. Обычное сочетание существующих компонентов не требует отдельного разрешения; новый публичный компонент, вариант или визуальное правило обсуждается до добавления.

Если чего-то не хватает, пользователь выбирает один из вариантов: собрать решение из имеющихся элементов либо согласовать расширение UI Kit. Во втором случае агент применяет процедуру `sdlc-ui-kit`, обновляет общую реализацию и витрину, затем продолжает исходный экран. Обходить это решение локальной копией компонента нельзя.

Если UI Kit ещё нет, создание экрана сначала проходит через его подготовку под текущий сценарий. Это не запускает всю цепочку SDLC и не требует повторного описания задачи.

### UI review

Пользователь указывает экран, маршрут, набор компонентов или изменение. Скилл фиксирует проверяемый код и версию UI Kit, изучает исходники и открывает отрисованный интерфейс. Проверяет только согласованные правила, варианты, состояния и размеры экранов в выбранном объёме.

Отчёт показывает:

- Что проверено и какие проверки недоступны.
- Где находится расхождение и какое правило или компонент UI Kit служит основанием.
- Что видно пользователю; скриншот или визуальное выделение, когда это помогает понять замечание.
- Предлагаемое решение: исправить UI по действующему набору либо обсудить расширение UI Kit.

Review создаёт только отчёт и его доказательные материалы. Код приложения, UI Kit, настройки и исходные эталоны не меняются. Для применения предложений нужен отдельный запрос пользователя.

## Проверяемые требования

| ID | Требование | Исходный результат |
| --- | --- | --- |
| R1 | UI Kit определяется через интервью под первые выбранные сценарии; принятые решения не спрашиваются повторно | O1 |
| R2 | Витрина и рабочие экраны используют общие реализации компонентов и стилей в стеке проекта | O2 |
| R3 | В brownfield канонический набор выбирается после исследования и показа вариантов; миграция старых экранов согласуется отдельно | O3 |
| R4 | Создание UI производит рабочий экран в приложении, а не отдельную имитацию; учитывает документы задачи и профиль проекта, если они есть | O4 |
| R5 | Недостающий компонент, вариант или правило обсуждается до добавления; согласованное расширение отражается в общей реализации, документации и витрине | O4, O6 |
| R6 | Review проверяет код и отрисованный UI в обозначенном объёме; выводы имеют конкретное основание в UI Kit | O5 |
| R7 | Review не исправляет продукт или UI Kit; отчёт отделяет несоответствия от пробелов в правилах и непроверенных частей | O5, O6 |
| R8 | UI-скиллы входят в семейство SDLC и работают самостоятельно; существующие политики проекта продолжают действовать | O1–O6 |
| R9 | Полный комплект `sdlc` содержит 10 скиллов, отдельный `sdlc-ui` — три UI-скилла; установка через Node, shell и вручную доставляет все необходимые инструкции и ссылки для четырёх поддерживаемых агентов | O1–O6 |
| R10 | После расширения набора используемые правила, исходники, витрина и записи о проверке согласованы; старое review не выдаётся за проверку нового UI Kit | O2, O6 |

## Примеры приёмки

| Ситуация | Ожидаемое поведение |
| --- | --- |
| Новый проект, нужен экран регистрации | Интервью определяет основу и компоненты этого сценария; не создаётся библиотека на все будущие случаи |
| В продукте пять вариантов кнопки | Скилл показывает различия, согласует набор и оформляет общую реализацию; не мигрирует все старые экраны |
| В React-проекте нужен новый экран | Используются исходники React и общие компоненты проекта, а не самостоятельная HTML-копия |
| Для экрана не хватает выбора диапазона дат | Агент обсуждает имеющиеся элементы или новый компонент; после согласованного дополнения обновляет витрину и возвращается к экрану |
| Кнопка выглядит правильно, но скопирована вместо использования общей | Review ссылается на исходники и фиксирует нарушение правила повторного использования |
| Используется общий компонент, но локальный CSS меняет его согласованный вид | Review связывает визуальное расхождение с переопределением и правилом UI Kit |
| Правила не определяют нужное поведение | Review отмечает пробел в UI Kit и предлагает решение, не придумывая обязательный стандарт |
| Браузерная проверка недоступна | Отчёт остаётся неполным: доступные выводы по коду сохранены, полного соответствия не заявляется |

## Границы и риски

Первая версия поддерживает web. Общий UX-аудит, произвольный редизайн, универсальная библиотека компонентов, новый UI-фреймворк и автоматическая миграция всего продукта не входят в объём.

Изменение общего компонента может затронуть существующие экраны. Перед таким изменением скилл показывает известный охват и согласует его с пользователем; при необходимости отделяет совместимое дополнение от миграции. Одинаковый внешний вид сам по себе не доказывает использование общей реализации, поэтому review сочетает исследование кода с визуальной проверкой.

Подробные контракты, интеграция с текущим репозиторием и проверка реализации — в [техническом приложении](technical.md).
